# Карта кода Ranuka

Этот файл описывает весь написанный код: какие есть файлы, что лежит в каждом,
как части вызывают друг друга и чем всё это проверяется. Самого кода здесь нет.

`docs/architecture.md` отвечает на вопрос «как устроен продукт».
Этот файл отвечает на вопрос «как устроен код, который его реализует».

## 1. Что готово, а что нет

| Часть | Состояние | Сколько кода |
| --- | --- | --- |
| `ranuka-core` — математика | Готова полностью | ~1050 строк, из них около половины — тесты |
| `ranuka-program` — программа | Готовы настройки платформы; создания токена и торговли нет | ~360 строк кода и ~440 строк тестов |
| `ranuka-sdk` — API для ботов | Заготовка | 8 строк |
| `ranuka-cli` — клиент | Заготовка, печатает версию | 7 строк |
| Сборка, проверки, CI | Работают | 4 файла |

Всего 41 тест: 30 в математике, 11 в программе.

## 3. Кто от кого зависит

```
ranuka-core  ◄──────  ranuka-program
     ▲
     └──────  ranuka-sdk  ◄──────  ranuka-cli
```

Стрелка означает «использует». `core` не использует никого, даже внешних
библиотек. Программа и SDK друг о друге не знают: их связывает только формат
инструкций и аккаунтов.

## 4. `ranuka-core`: математика

Набор чистых функций: на вход числа, на выход числа или ошибка. Ничего не
хранит, никуда не ходит, не знает о Solana. Поэтому его можно целиком
проверить тестами, а программа и бот получают одинаковый результат.

### 4.1. Три правила, зашитые в сам crate

Они записаны в первых строках `lib.rs` и проверяются компилятором и линтером,
а не вниманием автора:

| Правило | Что оно даёт |
| --- | --- |
| Без стандартной библиотеки (`no_std`) | Crate собирается внутри программы Solana |
| `unsafe` запрещён | Нет ручной работы с памятью |
| Запрещена арифметика без проверки переполнения | `+`, `-`, `*`, `/` в коде расчёта не пройдут линтер; каждое действие либо даёт результат, либо возвращает ошибку |

### 4.2. Файлы по порядку

**`constants.rs` — числа протокола.** Единицы измерения (лампортов в SOL, знаков
у токена, базисных пунктов в 100%) и комиссия: значения по умолчанию и жёсткие
пределы. Если нужно поменять комиссию по умолчанию или предел — это здесь.

**`error.rs` — что может пойти не так.** Один список `CoreError` из шести
причин: нулевая сумма, переполнение, не хватает токенов или SOL, комиссия выше
предела, кривая заполнена, некорректное расписание комиссии. Ни одна функция
`core` не «падает»: любая проблема возвращается как одна из этих ошибок.

**`types.rs` — данные.** Три типа, вокруг которых построено всё остальное:

| Тип | Что это | Когда меняется |
| --- | --- | --- |
| `CurveParams` | Стартовые параметры кривой: виртуальные резервы, сколько токенов продаётся, эмиссия. Значения из ТЗ лежат в `CurveParams::DEFAULT` | Никогда: одни для всех токенов |
| `Reserves` | Текущее состояние кривой: виртуальные SOL и токены (определяют цену), реальные SOL и токены (что реально лежит) | После каждой сделки |
| `Quote` | Результат расчёта сделки: SOL через кривую, токены, комиссия | Создаётся на каждую сделку |

У `Reserves` есть три вспомогательных действия: создать стартовое состояние,
узнать, заполнена ли кривая, и посчитать произведение резервов `k`.

**`math.rs` — умножение с делением.** Две внутренние функции: «a × b ÷ d
с округлением вниз» и «то же с округлением вверх». Промежуточный результат
считается в 128 битах, поэтому не переполняется. Все формулы цены сводятся
к этим двум функциям, и направление округления всегда выбрано явно.

**`fee.rs` — расписание комиссии.** Тип `FeeSchedule` из трёх чисел: обычная
комиссия, стартовая комиссия и длина окна в слотах. Умеет три вещи:

- проверить себя на жёсткие пределы (`validate`);
- сказать комиссию на продажу — всегда обычная;
- сказать комиссию на покупку через N слотов после создания токена — линейное
  снижение от стартовой к обычной.

**`curve.rs` — цена.** Главный файл. Наружу отдаёт четыре функции и четыре
действия над типами:

| Функция | Вопрос, на который отвечает |
| --- | --- |
| `quote_buy_exact_in` | У меня бюджет X SOL вместе с комиссией — сколько токенов я получу? |
| `quote_buy_exact_out` | Мне нужно ровно N токенов — сколько это стоит? |
| `quote_sell` | Я продаю N токенов — сколько SOL получу? |
| `fee_for` | Какая комиссия с такой суммы при такой ставке? |
| `Quote::buy_cost` / `sell_proceeds` | Итог для покупателя (с комиссией) и продавца (за вычетом) |
| `Reserves::apply_buy` / `apply_sell` | Какими станут резервы после этой сделки? |

Расчёт и изменение состояния разделены намеренно: `quote_*` только считает,
`apply_*` только применяет. Бот может посчитать сколько угодно вариантов,
ничего не меняя.

### 4.3. Как считается одна покупка

```
бюджет в SOL, ставка комиссии, текущие резервы
        │
        ▼
1. проверки: ставка в пределах? кривая не заполнена? сумма не ноль?
2. отделить комиссию от бюджета → сколько SOL реально идёт в кривую
3. формула кривой → сколько токенов это даёт (округление вниз)
4. токенов больше, чем осталось? → урезать до остатка, пересчитать SOL
5. посчитать комиссию с итоговой суммы (округление вверх)
        │
        ▼
Quote { sol, tokens, fee }   ──►   apply_buy   ──►   новые Reserves
```

Ставку комиссии `curve.rs` получает готовым числом. Откуда она берётся —
из `fee.rs` по номеру слота — решает тот, кто вызывает: программа или бот.

### 4.4. Чем проверена математика

Тесты лежат в двух местах и отвечают на разные вопросы.

**Рядом с кодом, в каждом файле (26 тестов)** — «правильно ли считает каждая
функция»:

- сверка с эталоном: контрольные значения посчитаны отдельно от кода
  и совпадают до лампорта;
- границы: ноль, пыль, больше остатка, заполненная кривая, ставка выше предела;
- расписание комиссии: начало, конец и середина окна, монотонное снижение;
- предельные входы: самые большие возможные числа дают ошибку, а не сбой.

**В `tests/invariants.rs` (4 теста)** — «не ломается ли система целиком».
Собственный генератор случайных чисел с фиксированным зерном прогоняет длинные
последовательности случайных сделок и после каждой проверяет:

| Тест | Что доказывает |
| --- | --- |
| Инварианты на случайных последовательностях | Произведение резервов не уменьшается; виртуальные и реальные резервы движутся согласованно. 800 прогонов по 500 сделок при разных ставках, включая стартовую |
| Пул всегда может выкупить всё | После любой истории сделок пулу хватает SOL выкупить все токены, которые вне его |
| Круг не приносит прибыли | Купить и сразу продать нельзя в плюс, даже при нулевой комиссии. 20 000 попыток |
| Заполнение мелкими покупками | Кривая заполняется на те же ≈ 85,005 SOL, что и одной покупкой |

## 5. `ranuka-program`: программа в блокчейне

Программа — единственное место, где лежат деньги и состояние. Сама она ничего
не считает: формулы и пределы берёт из `core`. Её работа — проверить, кто
вызывает и с какими аккаунтами, изменить состояние и выпустить событие.

### 5.1. Четыре понятия Anchor, на которых построен код

| Понятие | Что это в коде |
| --- | --- |
| Аккаунт состояния | Структура с полями, которая хранится в блокчейне (`Global`) |
| Список аккаунтов инструкции | Структура, где перечислено, какие аккаунты нужны инструкции и какие условия для них обязательны. Anchor проверяет эти условия до запуска основного кода |
| Обработчик | Функция с самой логикой инструкции; запускается, только если все условия выполнены |
| Событие | Запись о том, что произошло; её читают боты и интерфейс |

Каждая инструкция в коде — это пара «список аккаунтов + обработчик».

### 5.2. Файлы по порядку

**`lib.rs` — вход.** Объявляет адрес программы и перечисляет все инструкции.
Каждая инструкция здесь — одна строка, которая передаёт управление обработчику
из папки `instructions/`. Чтобы узнать, что умеет программа, достаточно
открыть этот файл.

**`constants.rs`.** Seed, из которого вычисляется адрес аккаунта настроек,
номер версии формата аккаунтов и адрес системного загрузчика программ.

**`error.rs`.** Три ошибки: нет прав, расписание комиссии вне пределов, нет
назначенного преемника. Номера ошибок — часть публичного интерфейса: новые
добавляются только в конец.

**`events.rs`.** Три события: настройки изменены, преемник назначен, админ
сменился. Событие «настройки изменены» несёт все новые значения целиком.

**`state.rs` — аккаунт `Global`.** Один на всю платформу:

| Группа полей | Поля |
| --- | --- |
| Служебные | номер версии формата, bump адреса |
| Управление | админ, назначенный преемник |
| Комиссия | получатель, обычная ставка, стартовая ставка, длина окна |
| Параметры кривых | стартовые виртуальные резервы, сколько токенов продаётся, эмиссия |
| Запас | 64 пустых байта под будущие поля |

Все поля фиксированного размера, поэтому их положение в аккаунте не сдвигается:
клиент может читать одно поле напрямую, не разбирая весь аккаунт.

### 5.3. Инструкции

| Инструкция | Файл | Кто может вызвать | Что проверяет | Что делает |
| --- | --- | --- | --- | --- |
| `initialize` | `initialize.rs` | Владелец права на обновление программы | Подписант совпадает с upgrade authority; аккаунт настроек ещё не создан | Создаёт `Global`: подписант становится админом, комиссия и параметры кривой берутся из значений по умолчанию в `core` |
| `set_config` | `set_config.rs` | Админ | Подписант — админ; новое расписание проходит проверку пределов из `core` | Записывает новую комиссию и получателя |
| `propose_admin` | `admin.rs` | Админ | Подписант — админ | Записывает преемника; нулевой адрес отменяет |
| `accept_admin` | `admin.rs` | Преемник | Преемник назначен; подписант — именно он | Делает его админом, очищает поле преемника |

Каждая инструкция в конце выпускает событие.

**Как `initialize` узнаёт владельца программы.** У каждой обновляемой программы
Solana есть служебный аккаунт, где записано, кто вправе её обновлять. Адрес
этого аккаунта однозначно вычисляется из адреса программы, поэтому подменить
его нельзя. `initialize` читает из него владельца и сравнивает с подписантом.

### 5.4. Где программа опирается на `core`

| Что нужно программе | Откуда берёт |
| --- | --- |
| Комиссия по умолчанию при инициализации | `FeeSchedule::DEFAULT` |
| Стартовые параметры кривой | `CurveParams::DEFAULT` |
| Проверка, что новая комиссия в пределах | `FeeSchedule::validate` |

Пределы комиссии нигде не продублированы: они записаны один раз в `core`.

### 5.5. Тесты программы (`tests/config.rs`, 11 тестов)

Тесты запускают настоящую скомпилированную программу внутри LiteSVM —
лёгкой копии среды исполнения Solana, работающей прямо в процессе теста.
Сеть и валидатор не нужны.

В начале файла лежит общая обвязка: подготовка среды, отправка одной инструкции,
чтение настроек, сборка каждой из четырёх инструкций. Сами тесты короткие
и делятся на три группы:

| Группа | Что проверяется |
| --- | --- |
| Инициализация (6) | Записываются значения по умолчанию; отказ постороннему; отказ при подменённом служебном аккаунте; отказ, если тот принадлежит не загрузчику; отказ для программы без права обновления; повторная инициализация невозможна |
| Настройки (3) | Админ меняет комиссию и получателя; отказ не-админу; отказ для каждого вида выхода за пределы, а сами пределы допустимы |
| Передача управления (2) | Полный путь в два шага с отказами на каждом; отмена назначенной передачи |

Отказ в тестах проверяется по точному номеру ошибки, а не по факту неудачи.

## 6. `ranuka-sdk` и `ranuka-cli`: заготовки

**SDK** сейчас делает одно: отдаёт `core` под именем `math`, чтобы бот мог
считать котировки тем же кодом, что и программа. Объявлена опция `rpc` для
будущих сетевых модулей; сами модули появятся в вехе 4.

**CLI** — бинарник `ranuka`, который печатает свою версию. Команды появятся
в вехе 5, интерфейс — в вехе 6.

## 7. Сборка и проверка

### 7.1. Файлы настройки

| Файл | За что отвечает |
| --- | --- |
| `Cargo.toml` (корневой) | Список четырёх частей; версии общих зависимостей в одном месте; общие правила линтера; настройки release-сборки, включая проверку переполнения |
| `Cargo.toml` в каждой части | Имя, зависимости и опции этой части |
| `Cargo.lock` | Точные версии всех библиотек; обновляет CI |
| `Anchor.toml` | Имя программы и её адрес для Anchor |

### 7.2. Одна команда на всё: `scripts/check.sh`

```
1. Anchor установлен? ── да ──► собрать программу
                       └ нет ─► тесты программы будут пропущены (в CI — ошибка)
2. форматирование: код оформлен единообразно
3. линтер: любое предупреждение считается ошибкой
4. тесты
5. если тесты программы пропущены — явное сообщение об этом
```

### 7.3. Автоматическая проверка: `.github/workflows/ci.yml`

При каждой отправке кода GitHub поднимает чистую машину и выполняет:

```
установить Rust, Solana CLI и Anchor
        ▼
запустить scripts/check.sh   (сборка программы + все проверки)
        ▼
на рабочей ветке: если изменился Cargo.lock — сохранить его в ветку
```

Это единственное место, где программа реально собирается.

### 7.4. Как изменение попадает в `main`

```
ветка wip/…  ──►  CI  ──►  зелёный?  ──►  main
                              │
                              └─ красный: правка в той же ветке, снова CI
```

В `main` попадают только изменения, прошедшие CI.

## 8. Сквозной пример: смена комиссии

Что происходит, когда админ меняет обычную комиссию на 0,5%:

```
клиент собирает инструкцию set_config с четырьмя значениями
        ▼
lib.rs                     находит инструкцию, передаёт в set_config.rs
        ▼
set_config.rs (аккаунты)   Anchor проверяет: адрес Global верный? подписант — админ?
        ▼
set_config.rs (обработчик) собирает FeeSchedule из присланных чисел
        ▼
core / fee.rs              validate: всё в пределах?
        ▼
state.rs                   новые значения записаны в Global
        ▼
events.rs                  выпущено событие ConfigUpdated
```

Если любая проверка не проходит, транзакция отменяется целиком и состояние
не меняется.

## 9. Чего в коде ещё нет

| Что | Где появится | Что уже готово для этого |
| --- | --- | --- |
| Аккаунт кривой `BondingCurve` | `state.rs` | Тип `Reserves` в `core` — его содержимое |
| `create`: выпуск токена и кривой | новый файл в `instructions/` | Параметры кривой уже лежат в `Global` |
| `buy_exact_in`, `buy_exact_out`, `sell` | новые файлы в `instructions/` | Вся математика и расписание комиссии в `core` |
| `collect_fees`, `migrate` | новые файлы в `instructions/` | — |
| События сделок | `events.rs` | — |
| Модули SDK | `crates/ranuka-sdk/src/` | Опция `rpc`, реэкспорт математики |
| Команды и TUI | `crates/ranuka-cli/src/` | Бинарник `ranuka` |

Новая инструкция всегда добавляется одинаково: файл в `instructions/`, строка
в `instructions.rs`, строка в `lib.rs`, события в `events.rs`, ошибки в конец
`error.rs`, тесты в `tests/`.
